# Security model

The GNOME interface, command-line client, and desktop event observer run as the signed-in user. The root D-Bus service derives the user's UID from the sender connection and invokes fixed backend executables. Administrator authentication approves work for the caller; it does not change the owner to the administrator who supplied credentials. Requests cannot choose a different UID or executable, inject arbitrary environment variables, or select a privileged execution scope. The small set of desktop and GnuPG environment hints accepted from the client is validated and used only for unprivileged owner processes. Results are private to their job owner and sensitive results expire.

## Authorization sessions

Metadata and private diagnostic inspection remain available without management authorization. Accessing repository data, changing records, and vault operations require authorization. A reusable management session is bound to the verified UID, unique D-Bus connection, and the caller's actual active, local, unlocked logind session. It lasts no longer than eight hours and is invalidated by explicit lock, connection loss, desktop lock, logout, suspension, loss of the active session, service restart, policy change, revocation, or expiry. Another connection from the same UID cannot reuse it. The service checks authorization again for protected work; a user-supplied session identifier cannot establish the grant.

The normal administrator prompt is handled by Polkit and its authentication agent. OctoVault never reads or stores administrator passwords. Manually opening the desktop requests authorization once; cancelling retains metadata inspection, and background activation does not initiate an administrator prompt. Supported headless or remote operations use fresh administrator authorization for each operation, without a reusable desktop session. A terminal authentication agent does not make a remote connection eligible for a local-session grant.

Ending authorization prevents new protected work. It does not close a mounted vault, erase decryption keys already in use, or cancel active jobs. The UI displays vault state separately. Saved vault close policies continue to protect open vaults independently of management authorization.

## Personal access and execution scope

An administrator can enroll eligible local accounts without adding them to sudo. Grants are stored in the root-owned, mode-0600 `/var/lib/octovault/access.json`; they match both the account name and UID. Starting an enrolled account's personal session verifies the grant without another administrator prompt. Granting or revoking another account's access requires fresh administrator authentication. Revocation invalidates personal sessions and prevents future personal scheduled backups. Jobs already running finish safely, and saved vault safety-close policies remain in force.

Each vault, destination, repository, and backup plan retains an `execution_scope`. Missing scope on an older record means `system`, preserving its existing administrator-managed behavior. A personal session cannot operate or modify system-scope resources, upgrade a resource's scope, or combine personal and system backup resources. System management can operate an existing personal record without changing its scope. Saved schedules retain and enforce the record's scope rather than inheriting the system scheduler's root identity. A personal schedule requires a current personal grant when it starts, but does not require an open application session.

All personal Restic operations, including backup, browsing, checking, restore, and local or remote repository access, run with the owner's operating-system identity. Source reads, symlink targets, repository writes, SSH connections, and restore targets remain subject to that user's filesystem permissions. Personal restoration cannot preserve arbitrary ownership or write protected system paths. System-scope operations retain their administrator-approved privileges. Credential preparation and state persistence stay in the privileged service; required credentials are made temporarily available to the permitted owner process. Other malicious software already running as that user can access the same active credentials and data.

Recovery disclosure is separately authenticated each time. Personal access permits only personal-scope repository recovery and requires the owner's authentication; recovery through system management requires administrator authentication. Personal access does not authorize forced vault closure or enabling force-close policies. Cryptographic passphrases, OpenPGP private-key authentication, and YubiKey PIN/touch requirements are independent of all operating-system authorization.

## Process and storage boundaries

The GNOME process disables core dumps and sets `PR_SET_DUMPABLE=0` because it handles passphrases and recovery information. Desktop portals can reject this process when they cannot inspect `/proc/PID/root`. File and folder navigation therefore uses GTK's standard in-process file chooser. The application does not temporarily weaken process protection, change global desktop settings, or require elevated privileges to browse files. The selected paths still pass through the normal service authorization and validation when an operation is submitted.

Record directories under `/var/lib/octovault/users/UID` are root-owned with mode 0700; JSON records and encrypted credentials are mode 0600. Saved configuration is data, never sourced shell code. Arguments are passed as arrays rather than evaluated command text. The adapters invoke the installed encryption and backup engines.

Repository and remote-access secrets are encrypted by `systemd-creds`. Automatic key selection uses the host's supported key protection. Where TPM support is unavailable, host-key encryption is still encryption, but copying the credential ciphertext together with its host decryption key defeats that binding. This is not equivalent to TPM-backed or user-present protection. It must never be described as secure against a compromised root account.

An unattended backup requires usable credentials while it runs. Secrets can therefore exist briefly in process memory, inherited descriptors, restrictive runtime files, or a child process's environment. OctoVault avoids secret command-line values, persistent plaintext configuration, diagnostic output, and application logs. A root attacker can read runtime secrets, intercept an authorized process, replace binaries, or read an already mounted vault. Hardware-backed keys limit key export but do not make a compromised authorized session trustworthy.

Keep recovery information in an independently secured password manager or other offline recovery location. Protect that vault separately. A password manager on the same unlocked compromised desktop does not provide an independent boundary. A lost repository password cannot be reconstructed from encrypted backup data.

Tomb keys, encrypted containers, and Restic repositories retain their upstream formats. Image/text concealment hides a key carrier; it does not replace cryptographic protection or make weak passphrases strong. Hardware tokens retain their PIN/touch requirements. User-installed executable hooks run with the vault owner's identity; treat them as trusted programs because they can read open data. Do not import unreviewed hooks or scripts.

Vault mounts must be visible to the user session. OctoVault enforces `nodev` and `nosuid` on opened vault filesystems, including imported vaults, so device nodes, setuid/setgid executables, and file capabilities within a vault cannot grant privileges through that mount. The privileged service intentionally does not create a private mount namespace using `ProtectSystem`, `ProtectHome`, `PrivateTmp`, or `PrivateDevices`; those directives can prevent bind mounts from appearing at their intended host paths. This makes strict authorization, path validation, ownership, and a fixed subprocess interface particularly important.

Sleep protection runs before the actual systemd suspend/hibernate executor through required ordered dependencies. If a configured vault cannot close, the helper fails and prevents that executor from proceeding. Forced power loss and a forcibly bypassed shutdown cannot be made into orderly close operations. A hard stop ends access to RAM-backed encryption mappings, but can leave filesystem or application writes incomplete. Force-close policies can kill processes and should be chosen deliberately.

Backup integrity checks validate repository structures and optionally read stored data. They are not a substitute for a successful restore test, nor can they prove an application database was transaction-consistent at backup time. Repository retention and pruning are separate operations, with retention preview available before deletion.

Security reports should be made privately to the project maintainer through the repository's security reporting channel when available. Do not publish credentials, raw recovery output, private keys, or personally identifying file listings in issues or CI artifacts.

The [authorization design](authorization.md) documents the required verification boundaries. Unit tests that bypass Polkit validate framing and request handling only. Authorization integration must exercise the production daemon with real system D-Bus, logind, Polkit, PAM, and distinct administrator and non-sudo accounts; software OpenPGP coverage does not establish physical YubiKey PIN/touch behavior.
